# .design

tingly-fuse 的设计记录：为什么这样做、做过什么取舍、接下来分几步。代码回答"现在是什么样"，这里回答"为什么是这样"。

| 文件 | 内容 | 何时更新 |
|---|---|---|
| [architecture.md](architecture.md) | 当前架构：目标、核心原则、目录布局、spawn/exec/push/drop 流程、后端契约 | 架构变了就改，保持和代码一致 |
| [roadmap.md](roadmap.md) | 分步推进的路线：每一步的范围、状态、验收方式 | 每完成或调整一步就改 |
| [decisions/](decisions/) | 决策记录（ADR），一个决定一个文件，编号递增 | 做了影响设计的决定就加一篇，不改旧的 |
| [research/](research/) | 前期调研：行业方案对比、同一路径 overlay 的演示脚本 | 基本不改，作为背景留存 |

基准测试的数据和报告在 [../bench/](../bench/)，结论摘要见 [decisions/](decisions/) 里引用它的条目。

## 约定

- **改设计的 PR 要同时改这里。** 动了架构就更新 architecture.md；做了取舍就新增一篇决策；一步做完就更新 roadmap.md 里的状态。
- **决策记录只追加。** 想推翻旧决定，新写一篇，状态写"取代 NNNN"，并把旧的状态改成"已被 NNNN 取代"，不要删改旧内容。
- **决策模板：** 状态 / 背景 / 决定 / 理由 / 后果。写清楚被放弃的选项，后面的人才不会重复讨论。
- 记录写事实和理由，不写进度流水账；进度只放在 roadmap.md。
